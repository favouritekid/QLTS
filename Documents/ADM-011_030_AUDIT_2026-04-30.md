## TL;DR

ADM-011 là **race condition thật** trong `bulk_assign` — 2 manager
cùng đơn vị bulk assign trùng profile sẽ silently mất write. Severity
P2 (blast radius nhỏ + audit log capture đủ để recover thủ công)
nhưng **không có lock nào** trong code path hiện tại.

ADM-030 là **FE work** (tooltip + highlight cho bulk approve UI),
hoàn toàn độc lập với ADM-011 về kỹ thuật. Memory bundle chỉ vì cùng
Wave 7. Tách thành 2 PR.

Trước khi fix ADM-011, **cần benchmark** — pessimistic lock per
profile có thể tăng latency 50-100ms × N profile + tạo deadlock risk
khi 2 manager bulk cùng tập profile.

## Phần 1 — ADM-011: Bulk Assign Race Condition

### Code path hiện tại

**Router** `routers/admissions.py:449-466` (`POST /admissions/bulk/assign`):
```python
result = await admission_service.bulk_assign(...)
await db.commit()
return schemas.BulkActionResponse(**result)
```

**Service** `services/admission_service.py:8296-8393` (`bulk_assign`):
```python
for profile_id in profile_ids:
    profile = await repo.get_profile_by_id_with_lead(profile_id)
    # ... IDOR check ...
    profile.lead.assigned_officer_id = officer_id   # ← NO LOCK
    success_count += 1
    await audit_service.log_changes(...)
await db.flush()
```

### Cụ thể race scenario

1. Manager A (cùng unit) click "Bulk assign profiles [1,2,3] → officer X"
2. Manager B click "Bulk assign profile [2] → officer Y" gần như đồng thời
3. A.session reads `profile_2.lead`, sets `assigned_officer_id=X`,
   chưa commit
4. B.session reads `profile_2.lead`, sets `assigned_officer_id=Y`,
   commit **TRƯỚC**
5. A.session commit → overwrite Y → `profile_2 = X`. **Manager B's
   intent silently lost** (không lỗi, không alert).

### Tại sao không có lock?

So sánh với `bulk_approve` (line 7826) — chính xác cùng pattern
nhưng có:
- `with_for_update()` per profile (pessimistic row lock) — line 7882
- Optimistic `version` check per profile — line 7904
- Per-item failure shape: profile fail → `failed_ids[]` + `errors[]`

`bulk_assign` không có **bất kỳ** lock nào (cả pessimistic lẫn
optimistic). Profile model **đã có** column `version` (admission.py:163)
— bulk_assign chỉ cần đọc + check.

### Existing safety nets (đã có)

| Safety | Source | Note |
|---|---|---|
| Permission gate (manager/admin only) | line 8320 | Block officer/user |
| Officer must be active + role=officer | line 8333-8336 | M4 fix |
| Officer unit match assigner unit | line 8339-8341 | M4 fix |
| IDOR per profile (manager limited to unit) | line 8357 | |
| Audit log mỗi assignment | line 8369 | `source="bulk_api"` |

→ Race chỉ silently mất write vào `lead.assigned_officer_id`. Không
phá quota, không phá state machine, không leak cross-unit.

### Severity assessment

| Aspect | Score |
|---|---|
| Likelihood | LOW (cần 2 manager cùng unit + thao tác trùng profile trong cửa sổ ms) |
| Impact | MEDIUM (silently lost write, audit log capture cả 2 attempt nên có thể recover) |
| Detectability | LOW (không lỗi, không log warn — chỉ thấy qua diff audit log) |
| **Net P-level** | **P2** (như memory đã chốt) |

## Phần 2 — Fix Options (cần benchmark)

### Option A — Optimistic lock per profile

```python
for item in items:  # items[i] = {profile_id, version}
    profile = await repo.get_profile_by_id_with_lead(profile_id)
    if expected_version != profile.version:
        failed_ids.append(profile_id)
        errors[profile_id] = "Version mismatch — refresh and retry"
        continue
    profile.lead.assigned_officer_id = officer_id
    profile.version += 1   # bump để invalidate concurrent A
```

**Pros**:
- Zero new DB lock — chỉ thêm read column
- Per-item failure mode rõ ràng (giống bulk_approve)
- FE đã có version field trong response sẵn

**Cons**:
- Thay shape API: `profile_ids: List[int]` → `items: List[{profile_id, version}]` — breaking change
- FE bulk-assign UI cần track version cho mỗi selected profile
- Manager B's attempt chưa chắc thấy version mới của A (race vẫn có window)

**Race window thu hẹp**: write của A bump version, B đọc sau A
commit sẽ thấy version mới → B fail-fast `Version mismatch`. Trước
A commit, race vẫn còn (B đọc cùng version cũ với A).

### Option B — Pessimistic lock per profile (`SELECT FOR UPDATE`)

```python
for profile_id in profile_ids:
    stmt = (
        select(models.AdmissionProfile)
        .where(models.AdmissionProfile.id == profile_id)
        .options(selectinload(models.AdmissionProfile.lead))
        .with_for_update()
    )
    profile = (await db.execute(stmt)).scalar_one_or_none()
    profile.lead.assigned_officer_id = officer_id
```

**Pros**:
- Zero race — second writer chờ first commit
- API shape không đổi (backward compat cho FE)

**Cons**:
- N row locks per request (N = số profile bulk)
- Deadlock risk khi 2 manager bulk cùng tập profile theo thứ tự khác
- Latency tăng dưới load (cần benchmark)

**Mitigation deadlock**: sort `profile_ids` ascending trước loop —
mọi caller lock theo cùng thứ tự → no deadlock cycle.

### Option C — Pessimistic lock trên lead row (where the write actually happens)

```python
for profile_id in profile_ids:
    # Lock the LEAD row, not the profile (write is on lead.assigned_officer_id)
    stmt = (
        select(models.Lead)
        .join(models.AdmissionProfile)
        .where(models.AdmissionProfile.id == profile_id)
        .with_for_update()
    )
    lead = (await db.execute(stmt)).scalar_one_or_none()
    lead.assigned_officer_id = officer_id
```

**Pros**:
- Lock đúng table chứa column được write
- Tránh false sharing với các update khác trên admission_profile

**Cons**:
- Phức tạp hơn (2-table join + lock)
- IDOR check cần adapt (đang đọc `profile.lead.unit_id`)

### Recommend

**Phase 1 (ship trước)**: **Option B** + sort ascending để tránh
deadlock. Backward compat, thay đổi nhỏ. Cần benchmark trước khi
ship để xác nhận latency acceptable dưới expected bulk size (50-100
profiles).

**Phase 2 (sau)**: thêm optimistic version check **bên cạnh**
pessimistic lock — defense in depth, đổi API shape khi FE bandwidth
sẵn. Không cần ship cùng phase 1.

## Phần 3 — Benchmark Plan

### Câu hỏi cần trả lời

1. **Latency penalty** của `with_for_update()` trên 50/100/200 profile
   trong 1 request (no concurrent contention)?
2. **Throughput penalty** khi 2-3 manager bulk concurrent (worst case
   officer team + admin)?
3. **Deadlock rate** với sort-ascending mitigation?
4. **Memory penalty** trên Postgres (`pg_locks` size dưới load)?

### Setup

**Local stack**: dùng `qlts-w2` Docker (port-isolated, đang chạy).

**Seed data**: 200 admission_profile + 200 lead trong unit_id=1, manager
A + B + admin đăng nhập.

**Test script**: `tests/perf/test_bulk_assign_benchmark.py` (mới).
- Concurrency: 1 / 2 / 3 manager đồng thời
- Bulk size: 10 / 50 / 100 / 200
- Iterations: 20 lần mỗi cell
- Output: latency p50/p95/p99, deadlock count, success rate

### Pass criteria (đề xuất)

| Metric | Threshold |
|---|---|
| p95 latency 100-profile bulk | < 2s |
| Deadlock rate (3 concurrent, 200-profile) | 0% |
| Success rate | ≥ 99.5% (per-item failures OK) |

Nếu fail → fallback Option C (lead-only lock) hoặc giảm batch size limit.

### Effort

- Seed script: 30min
- Benchmark script: 1h
- Run + analyze (multiple iterations): 1h
- Document baseline + post-fix delta: 30min
- **Total benchmark phase**: ~3h (chưa tính fix code)
